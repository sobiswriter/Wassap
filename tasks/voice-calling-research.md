# Persona voice calling: research and proposed implementation

Researched and implemented locally on 18 October 2026. Follow-ups below supersede the initial implementation/proposal where they differ. Initial verification used mocks; later generic real Google probes verified Live audio, tuned speech detection and global text summarization. No deployment, SDK upgrade or physical microphone/device validation performed. Hardware checks remain open.

## Initial local implementation outcome

- Added root-owned full/compact call UI, bundled doodles, actual Live capture/playback/interruption, mute/audio controls, 15-minute safety limit, connection resumption and prebuilt persona voices. Custom voices remain configured for voice notes, with an explicit call-voice notice.
- Both existing provider modes retained: personal-key Live SDK connection and cookie/Origin-authenticated standalone Vertex WebSocket relay. Explicit server `ws` dependency, Vite dev/preview upgrade wiring, independent `VERTEX_LIVE_LOCATION` and dedicated 300-second Vercel duration. No shared key or access token is returned to the client.
- New separate call-recovery database, call-history metadata and call-ID-linked diary memories. Full call transcript is represented as one labeled diary event to retain early/late content. At least 60 connected seconds and two-way speech are required. Summaries are persisted before transcript removal and remain retryable; existing memory toggles/data stay intact.
- Service-worker call notifications offer End and restore controls where supported. Durable End intent, stale-call isolation, cross-tab Web Lock, orphan-session bounds, delayed-permission cleanup and per-persona queued/background text coordination are implemented. End has the documented suspended-page limitation. Clearing/deleting chats or call messages removes recovery records.
- Automated verification includes 25 tests, TypeScript/build, relay mock integration, and isolated Chrome tests using a synthetic microphone and mocked provider/diary transports. Both provider wire paths, PCM capture/output/interruption, mute, compact mode, resumption, late microphone permission, denial, responsive widths, whole-call diary and persistence are exercised. Existing mobile/archive/selection/polish/reload browser scripts passed. These checks are not real Google calls or Android notification/background certification.
- Owner still owns commit/push/deployment. Version labels remain 1.9.7 pending release decisions; shell cache v19 refreshes capture/calling assets. Physical Android audio/echo/Bluetooth/Home/lock and actual Google/hosting access are the remaining release gates.

## Accepted requirements and platform decision (18 October 2026 follow-up)

This section supersedes the earlier foreground-only and optional-summary assumptions below. The owner explicitly selected **browser/PWA only, with device-dependent background support**, after being offered a native Android calling option. No Android wrapper, APK, native service or new native project is authorized by that choice.

### Reference UI and interaction

The owner supplied two WhatsApp Android screenshots: a full call screen with doodle wallpaper, name/status, central round avatar and rounded bottom controls; and a minimized **in-app** call strip above the conversation, plus voice-call history cards. Reproduce their hierarchy, dark surfaces, control sizing/spacing and collapse/restore feel using Wassap's design tokens and actual persona avatar. The system status bar and native notification are distinct from that in-app strip. Do not copy private chat content from the reference into fixtures/assets.

Keep Speaker/audio routing, Mute and End truthful to device capability; browser output-device control is a compatibility check, not a guaranteed earpiece/speaker switch. Video, add-person and Share are outside the voice-call scope; settle whether to omit or visibly disable reference controls rather than implement unrelated features or clickable no-ops. Replace the screenshot's end-to-end-encrypted subtitle with accurate AI-provider disclosure. Call status/timer starts from real connection readiness, not button press, and Back/collapse preserves the same session.

### PWA background and notification contract

Keep call ownership above the call screen so internal navigation does not end capture. Attempt continued audio while backgrounded, but test hidden/locked behavior on the owner's actual Android browser/PWA and phone. No promise of surviving browser termination, force-stop, OS process removal or indefinite lock-screen operation. Do not substitute a wake lock, silent audio loop or service worker for supported background microphone ownership.

Use the existing service worker notification infrastructure for a separate call notification with persona/status and End action when permission and actions are supported. Notification body restores the existing call screen. End dispatches a call-ID-scoped command to the owning page; persist the end request so it is honored before any reconnect when a suspended page wakes. A stale notification must never terminate a newer call. Acknowledge termination before reporting it completed, and close stale notifications on call end/reconciliation. Media Session hangup/microphone actions may enhance supported platforms, but feature detection does not establish Android UI support. Browser/OS determine notification layout, action visibility and dismissal behavior; a browser notification is not Android's native CallStyle template.

Explicit limit: if the owning page is suspended, a service-worker message cannot guarantee immediate microphone/socket cleanup. That matters especially for direct personal-key Live connections, which the service worker does not own. Test and communicate this limit instead of claiming notification End is universally immediate. Built-in relay disconnect/idle safeguards must stop orphaned upstream usage; an independently addressable server stop signal requires a verified cross-instance design and is not solved by a module-level map. Do not start an automatic reconnect after a persisted End request.

Sources: [web notification actions and OS-controlled appearance](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerRegistration/showNotification), [Media Session action availability](https://developer.mozilla.org/en-US/docs/Web/API/MediaSession/setActionHandler), [Chrome page lifecycle](https://developer.chrome.com/docs/web-platform/page-lifecycle-api). Android's alternative native mechanisms were researched but declined for this scope: [microphone foreground services](https://developer.android.com/develop/background-work/services/fgs/service-types), [CallStyle ongoing-call notifications](https://developer.android.com/develop/ui/compose/notifications/call-style).

### Context and automatic diary-style call recollection

At call start include persona identity/basics, bounded recent chat, relevant enabled past memory/call summaries and current call context. The call directive identifies a live voice conversation, preserves language/personality, and carries start time only when time sharing permits it. During the call the Live session maintains the current conversation; reconnect resumes that session rather than treating each utterance as a fresh call. Keep provenance separate so older recollections do not become claims about this call.

User requested automatic summarization after a successful call of about a minute. Working threshold: at least **60 seconds of connected time**, excluding ringing/setup/reconnection gaps, plus meaningful two-way transcript content. Under-threshold/failed/empty calls may retain accurate call history but do not invent diary content. Hang-up releases audio resources immediately; summary generation happens afterward and never holds the microphone open.

Build from the **whole call transcript**, including early and late events, speakers and interruption markers, not only the last few turns or the recent-chat seed. Reuse the existing diary generation/provider pipeline with a call-specific context/source label, first-person persona voice and matching language/dialect. Check `buildDiaryHistoryAndPrompt` before reuse: date-based proportional sampling must not silently omit most of a long single-day call. If input exceeds the verified model budget, use chronological bounded segments and merge their summaries; only introduce that extra work at the actual limit.

Save one editable/removable recollection per call in the existing memory system with additive call source/ID/duration metadata and a matching call-history record. Do not rename stores, clear messages, or force a disabled memory feature on. A subsequent text conversation/call should recall the saved recollection when memories are enabled. Repeated end events, notification actions and reconnects must not create duplicate call entries or summaries.

Persist transcript fragments incrementally so backgrounding/reload does not lose everything. Persist summary job status keyed by call ID; on network/provider failure leave it pending/retryable without fabricating a diary, and reconcile an already-saved memory before retrying. No exactly-once provider-billing claim is made when a response is lost. Avoid raw audio recording and server transcript logging. Limit temporary transcript retention to the agreed recovery/summary need; default final UX can show the summary rather than flooding chat with transcript bubbles. Final retention policy remains to be specified.

### Revised acceptance checks

- Full screen, compact in-app bar and call-history records match supplied reference proportions and transitions; collapse/restore retains one session and accurate mute/timer state.
- Android PWA/browser: Home, app switching, screen lock, silent listening, Bluetooth/headphones, return to app and notification End are measured on hardware. Repeat End during reconnect and against a stale notification. Record which states/devices work; do not advertise unsupported cases.
- 59-second, 60-second, failed/empty, interrupted and reconnected calls exercise the summary boundary. Include a distinctive fact near the start and another near the end; both must survive summarization and be recallable later. Preserve language, user/persona attribution and all existing settings/data.
- Hang-up from UI/notification prevents further audio/reconnection as soon as the owning page can execute; no duplicate summary and no stuck microphone after return. Test summary retry after restart and existing provider/auth regression gates.

## Recommendation and assumptions

Use `gemini-3.8-live` native audio for one-to-one, user-initiated persona calls. Keep current TTS for voice notes. First release assumes the app remains open, one active call per browser, microphone mute and hang-up, and a documented prebuilt Live voice. Group calls, video, incoming background calls, raw call recordings and custom-voice parity are separate decisions. These are proposed scope choices, not accepted product requirements.

Google distinguishes interactive Live audio from exact-script TTS. A record/transcribe/chat/TTS loop remains possible if custom voice fidelity becomes mandatory, but adds separate turn detection, interruption and cancellation work. Do not build both pipelines initially.

Sources: [Live model](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-live), [TTS distinction](https://ai.google.dev/gemini-api/docs/speech-generation).

## Provider routing and hosting

- Custom Gemini key: browser connects to Google's Live endpoint using the user's existing personal key. Keep the key in its current user-managed setting; never send it to the cloud relay or log it.
- Built-in Vertex: browser connects to a same-origin authenticated WebSocket relay; the relay opens the Vertex Live session with server credentials. Validate the existing cloud cookie and request Origin before upgrade; allow only the selected Live model, bounded setup/context/audio frames, supported voice/config, and permitted message types. Enforce connection/idle/call budgets and bounded buffers; close both sockets on termination. The shared passkey is not an individual user account, so cross-instance member quotas cannot be claimed from an in-memory counter.
- Gemini Developer API ephemeral tokens are a documented alternative if the owner explicitly chooses Developer API billing for built-in calls. They are not assumed to work with the existing Vertex service-account path. Lock their model/config, issue short-lived single-session tokens after backend authentication, and never return shared long-lived credentials or a broad GCP access token to the browser.
- Current Vercel documentation supports WebSockets in beta with Fluid Compute. First validate the existing deployment's support and routing with a minimal authenticated handshake, rather than assume old no-WebSocket guidance or introduce a new hosting service immediately. Existing `api/gemini/*.ts` has a 60-second maximum; a relay needs an explicit reviewed duration and reconnection strategy. Fluid Hobby maximum is 300 seconds; Pro/Enterprise have different maxima. A new connection may reach a different instance. Do not depend on process memory across reconnects.
- Vertex model documentation lists `us`, `eu`, and `us-central1`, not the app's current `global` default. Choose the supported Live location after latency/access checks, without changing text/TTS routing.

Sources: [Vertex session authentication](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/live-api/start-manage-session), [Vertex proxy example](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/live-api/get-started-websocket), [ephemeral tokens](https://ai.google.dev/gemini-api/docs/live-api/ephemeral-tokens), [Vercel WebSockets](https://vercel.com/docs/functions/websockets), [function limits](https://vercel.com/docs/functions/limitations), [Vertex Live model regions](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/gemini/3-8-live).

## Audio and session lifecycle

Browser microphone -> AudioWorklet capture/resampling -> mono signed 16-bit little-endian PCM at 16 kHz -> Live session -> 24 kHz PCM -> scheduled Web Audio playback.

Use the actual capture sample rate; a requested microphone rate is not a guarantee. Request echo cancellation/noise suppression and validate on speakerphone and headphones. Reuse existing PCM helpers where appropriate, but the complete-file WAV/24 kHz converter is not a streaming microphone pipeline. Keep PCM queues outside React rendering, bound network/playback queues, and process every content part in each event.

Use automatic speech detection initially. On interruption, stop active playback and discard queued audio immediately; ignore late audio from superseded turns. Mute must stop transmitting microphone samples and flush the audio stream as documented. Hang-up must release every microphone track, audio node, socket, timer and session handle, even if connection or permission is still pending. Closing a call while the permission prompt remains open must also dispose of a stream if permission resolves later.

Keep explicit connecting/active/reconnecting/ended/error states. Handle GoAway and resumable handles. Google documents roughly ten-minute connections and a fifteen-minute uncompressed audio session limit; context compression and session resumption address different limits. Hosting can force an earlier reconnect. Never reconnect after explicit hang-up, and never replay all microphone buffers or duplicate the greeting/transcript on reconnection. Resume handles stay session-scoped, not permanent settings or diagnostics.

Sources: [Live overview/audio formats](https://ai.google.dev/gemini-api/docs/live-api), [Live capabilities/VAD](https://ai.google.dev/gemini-api/docs/live-api/capabilities), [session management](https://ai.google.dev/gemini-api/docs/live-api/session-management), [AudioWorklet](https://developer.mozilla.org/en-US/docs/Web/API/AudioWorklet), [microphone API](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia), [echo cancellation](https://developer.mozilla.org/en-US/docs/Web/API/MediaTrackConstraints/echoCancellation).

## Persona identity and continuity

Reuse `buildFullPersonaSystemPrompt`, current profile/humane settings, schedule/time-gap/memory context helpers and existing context-sharing toggles. Adapt the shared builder minimally for live spoken conversation: texting abbreviations, multi-bubble instructions and the fixed 5-to-20-second voice-note directive should not drive a continuous call. Do not blindly append conflicting call instructions to the existing text prompt.

Seed bounded recent chat with explicit user/model roles and preserve enabled memories/schedule context. Avoid sending the same transcript in both system text and session history. Do not hydrate old photos/audio by default for an audio call. Keep the Live model separate from the two permitted text models and current TTS selectors. Omit unsupported thinking configuration for standard `gemini-3.8-live`.

Live's documented voice setup uses `prebuiltVoiceConfig.voiceName`. Test the persona's saved prebuilt voice. Google documents custom designed/replicated IDs for TTS; that does not establish Live support. If a persona uses a custom voice, show the chosen call voice explicitly and obtain a product decision on fallback rather than silently changing their voice.

Enable input/output transcripts for continuity. Proposed local storage is text-only, appended through the existing chat persistence path, with optional call ID/interruption metadata. Never feed stored call transcripts back through the ordinary send handler and generate another reply. Interrupted output must be marked partial: generated transcription is not proof that every word played or was heard. Deduplicate committed turns across reconnects. Transcript storage/UI is a product choice to confirm before implementation; do not add an automatic paid summary call by default.

Coordinate active calls with chat generation, scheduled check-ins, pending sends, notification replies and the existing single audio player. Suspend competing work for the called persona while retaining all queued messages; resume normal processing on exit. Service-worker reply routes need an explicit active-call coordination contract, not just a disabled composer. Other personas should continue normally. Native lock-screen/background microphone continuity is not promised by a browser-only first release.

## Conversation quality follow-up (18 October 2026)

The owner requested fewer false interruptions, lighter context, a natural pickup delay and persistent short-call transcripts. The implementation now supplies Live only name/description, voice delivery and a <=1,600-character summary of the latest 20 text messages (<=2,000 characters/message). It omits the full persona prompt, diaries, schedule, clock and user profile. The summary is a separate text request, prepared during locally synthesized 6–12 second ringback. Summary failure never falls back to forwarding raw messages. Microphone transmission and the greeting wait for pickup.

[Google's automatic VAD controls](https://ai.google.dev/gemini-api/docs/live-api/capabilities) allow low start/end sensitivity and a longer endpoint silence. Initial tuning uses 200 ms prefix padding and 900 ms silence, preserving genuine speech interruptions. Browser echo/noise cancellation stays enabled, automatic gain is disabled to avoid lifting background sound, and input batches shrink from 80 to 40 ms. [Google's best practices](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/live-api/best-practices) recommend 20–40 ms input chunks and compact, clear instructions. Playback gets 40 ms of scheduling margin. No local amplitude detector is added: loudness alone cannot establish intended speech, and a hard gate could clip quieter speakers. These values still need phone-specific calibration.

Short calls retain a labeled raw transcript in an expandable card and ordinary message text for future AI context. Calls of at least 60 connected seconds with usable transcript text receive the whole-call diary and expandable summary. Ring cancellation is distinct from connection failure. Temporary recovery text is removed only after the chat write succeeds. Already-discarded historical short-call transcripts cannot be reconstructed.

Controlled real Google checks used no private conversation or microphone recording: the tuned session accepted setup, produced zero response chunks/no transcription for four seconds of hum/two noise bursts plus silence, then transcribed a synthesized five-second sentence and returned 92,162 PCM bytes. The summary request succeeded in 4,841 ms in one test at global; the same text model returned 404 at us-central1, so text and Live regions are deliberately independent. These tests establish controlled functionality, not Android acoustic echo cancellation, noisy-room intent detection, Bluetooth or background survival. Shell cache v20 refreshes the changed worklet without clearing user databases.

## Chat continuity, expressive speech and visual input follow-up

Calls now retain full transcripts in dated chat events independently of diary success. The ordinary text model receives the call time/duration and summary (or transcript while no summary is available). Persona-specific time awareness defaults on; off suppresses automatic absence/frequency reactions across both providers and notification replies without changing the global clock setting.

The ringback is now a bundled, unmodified [CC0 recording by Kaga Sound](https://commons.wikimedia.org/wiki/File:Ringingsound.wav), rather than synthesized quiet tones. A dedicated media element is exempt from the call's other-media pause handler and is stopped at pickup/End; its source is precached offline.

For expressiveness, [Google's Gemini 3.8 Live migration docs](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-live) explicitly remove `enable_affective_dialog`; the older feature switch is not applicable. [Voice guidance](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/live-api/configure-language-voice) supports directing tone and accent through instructions. We added modest context-appropriate intonation/emotion guidance, preserving the persona's selected voice. [TTS documentation](https://ai.google.dev/gemini-api/docs/speech-generation) describes richer acting/style control in its separate synthesis models; using the same voice name does not establish identical expressiveness across TTS and Live. An audible A/B test is still needed; no obsolete flag or alternate voice pipeline was added.

Camera and screen sharing were researched only, per the owner's instruction. [Google's streaming guide](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/live-api/send-audio-video-streams) accepts sequences of JPEG frames, with 1 FPS and 768x768 recommended, alongside audio. A next update can sample camera frames acquired through getUserMedia, or a user-selected display/tab through getDisplayMedia, then send bounded JPEG frames through the existing Live session. The current Cloud relay accepts audio only and would need explicit MIME, frame-size/rate validation, cleanup on share-stop/End, local preview and camera switching. These are future work, not implemented controls.

[MDN's screen-capture compatibility data](https://github.com/mdn/browser-compat-data/blob/main/api/MediaDevices.json) currently lists desktop Chrome/Edge/Firefox/Safari support, no Chrome/Firefox Android capture, and iOS Safari support beginning with version 27. Check actual target versions rather than promising mobile screen sharing generally. Capture requires user permission and a secure context; screen sharing requires a fresh user gesture/selection. PWA installation does not itself add missing capture APIs. Visual frames increase context/cost, so send only while explicitly enabled. No camera or screen access was attempted during this task.

## Cost and unresolved decisions

Developer API currently lists $3/M audio input tokens and $12/M audio output tokens, with approximate equivalents $0.005 per input-audio minute and $0.018 per output-audio minute. Ten minutes of input plus five minutes of generated speech is about $0.14 for that audio alone; text context, session accounting, tools and hosting are additional. This is an illustrative calculation, not a fixed per-call quote. Vertex lists the same audio token rates; verify actual usage on each billing path. Capture aggregate latency/error/usage metrics without raw audio, transcripts or credentials in server logs.

Sources: [Developer API pricing](https://ai.google.dev/gemini-api/docs/pricing), [Vertex pricing](https://cloud.google.com/gemini-enterprise-agent-platform/generative-ai/pricing).

Before implementation, settle: whether prebuilt Live voice is acceptable for personas with custom voices; desired call transcript retention; foreground-only first release; initial duration/budget; and whether the target Vercel deployment enables the documented WebSocket beta. No need to decide video/group calling or install a realtime framework for this first feature.
